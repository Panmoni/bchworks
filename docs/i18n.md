# Localized content

How translated words are stored, found, drafted, reviewed and shown. The
locale list and routing live in `src/i18n/locales.ts` (PAN-376); UI strings
live in the message catalog (PAN-377). This page covers content
(collections, page prose and the JSON data files), the translation pipeline
(PAN-382) and how to add a language.

## Where translations live

| What | English | Translation |
|---|---|---|
| Collections (`post`, `upgrades`, `chips`, `compare`, `guides`, `reference`, `reports`) | `src/content/<collection>/<slug>.md` | `src/content/<collection>/<locale>/<slug>.md` |
| Page prose | `src/content/pages/<page>.yaml` or `.md` | `src/content/pages/<locale>/<page>.yaml` or `.md` |
| JSON data (`glossary`, `opcodes`, `projects`) | `src/data/<file>.json` | `src/data/i18n/<locale>/<file>.json` |

English stays at the collection root, so English ids and URLs never change.
Each English loader in `src/content.config.ts` skips the locale dirs. The
translations load into a parallel `<collection>L10n` collection (`chipsL10n`,
`pagesL10n`, …) whose ids are `<locale>/<slug>`, so they cannot collide with
an English id.

## Translation metadata

Every translated entry carries a `translation` block in its frontmatter (or
at the YAML top level). It is nested so it cannot clash with an entry's own
fields: chips and upgrades already have a `status`.

```yaml
translation:
  sourceHash: 94c72a8ec3bfeba7
  status: machine
  translator: Claude
```

| Field | Meaning |
|---|---|
| `sourceHash` | `hashSource()` of the English source file it was translated from: 16 hex chars of its SHA-256 |
| `status` | `machine` (a draft nobody has checked) or `reviewed` |
| `translator` | who or what made it |
| `reviewer` | who checked it; required when `status` is `reviewed` |

Zod checks all of it at build: a translation without `sourceHash` fails the
build. A translation never sets `lang` (its language is its locale dir) or
`slug` (its id is its path); the build rejects either. On an English-root entry `lang` names
the language it was written in, which is not always English: the Venezuela
guide is a Spanish original served at `/guides/venezuela`.

When the English source changes, its hash no longer matches the
translation's `sourceHash`, and the translation is stale.

## Finding a translation

`getLocalizedEntry(collection, slug, locale)` in `src/utils/l10n.ts` returns
the entry in that locale, or `null`. It never substitutes English; the
caller decides what `null` means. Pages read their copy through
`getPageCopy(id)` / `getPageEntry(id, locale)` in `src/utils/pages.ts`.

## Fallback policy

- **A whole page is never served in English at a locale URL.** No locale
  entry means no locale route: a locale's `getStaticPaths` lists only the
  slugs `getLocalizedEntry` finds. Astro's i18n `fallback` stays off.
- **An embedded fragment may fall back to English**, for example a glossary
  definition inside a Spanish page whose overlay lacks it. It must render
  inside an element with `lang="en"` and `data-l10n-fallback`, which
  `<LocalizedText>` (`src/components/common/LocalizedText.astro`) does for
  every value from `localizeRecord()`. Data the site keeps in English on
  every page (tag and category names) is marked the same way, through
  `englishData()` in `src/utils/l10n.ts`. `pnpm i18n:check:dist` lists every
  `data-l10n-fallback` element in `dist`.

`/es/prueba-i18n` is the fixture: it embeds the glossary term `utxo` under
an id no overlay holds, so it renders as `<span lang="en" data-l10n-fallback>`
however much of the glossary is translated.

## Page prose

A file in `src/pages/` holds layout and component calls. Its words live in
`src/content/pages/<id>.yaml` (structured props: headings, item lists,
calls to action) or `<id>.md` (long prose such as the legal pages), where
`<id>` is the page path with dashes (`chips/index.astro` → `chips-index`).
Text with inline links or emphasis is an HTML string, rendered with
`set:html`. Item arrays move whole, icons and links included, so a
translator copies the file and changes only the words.

A translated page must keep the English structure: the same keys, the same
list lengths, and the same values for identifier keys the page code reads
(`icon`, `href`, `url`, `collection`, `verdict`, `best`, `txid` and the rest
of `IDENTIFIER_KEYS` in `src/utils/localize.mjs`). `getPageEntry` throws at
build when it does not. Placeholders such as `{count}` stay as written and
may appear more than once.

## JSON overlays

`src/data/i18n/<locale>/<file>.json` holds only translatable fields, keyed
by the English record's `id`:

```json
{
  "utxo": {
    "definition": { "text": "Salida de transacción no gastada…", "sourceHash": "3f1c…" }
  }
}
```

`sourceHash` is `hashSource()` of that English field's value. A field the
pipeline wrote also carries `status`, `translator` and, once reviewed,
`reviewer`, as a content `translation` block does. The overlay
never holds untranslatable data, so the daily refresh
(`.github/workflows/refresh-data.yml`) never reads or writes it.
`localizeRecord(record, file, fields, locale)` merges it: a record or field
with no overlay, or whose `sourceHash` no longer matches the English text,
keeps its English text, marked as a fallback fragment. So a project the
refresh adds tomorrow, or a definition someone rewrites, shows in English
until someone translates it again.

## Orphans

A translation whose English id no longer exists is an orphan: left alone, it
would attach to whatever later reuses that id. `findOrphans()` in
`src/utils/localize.mjs` lists every content translation and overlay id
with no English original. `pnpm i18n:check` reports them and fails on one in
a live locale.

## Translation pipeline

The loop for every language: find what is missing or stale, machine-draft
it, have a native speaker review it, credit them. Code in `scripts/i18n/`.

### Three kinds of source

| Kind | English | Translation | Provenance |
|---|---|---|---|
| Catalog | `messages/en.json` | `messages/<locale>.json` | `messages/meta/<locale>.json`, keyed by message |
| Content | `src/content/<collection>/<slug>.<ext>` | `src/content/<collection>/<locale>/<slug>.<ext>` | its `translation` block |
| Overlay | `src/data/<file>.json` | `src/data/i18n/<locale>/<file>.json` | on each field |

The inlang message format has no room for metadata, so catalog provenance
sits in a sidecar file the compiler never reads. A message's `sourceHash` is
`hashSource()` of `JSON.stringify` of its English value, plural variants
included.

Each translated unit (a message, a file, an overlay field) is **missing**,
**stale** (its `sourceHash` differs from the English now) or **fresh**.

### Draft: `pnpm i18n:draft <locale>`

```sh
pnpm i18n:draft es --dry-run                       # list what it would draft
pnpm i18n:draft es --only 'src/content/chips/**'   # one area
pnpm i18n:draft es                                 # everything
```

It drafts every missing unit and every stale `machine` unit through the
Claude API (`ANTHROPIC_API_KEY` from the environment, model `MODEL` in
`scripts/i18n/claude.mjs`) and writes `status: machine`, the current
`sourceHash` and `translator: Claude`. `--only` takes a glob
matched against the English or the translation path.

**A person's work is held, never overwritten.** A `reviewed` unit that went
stale, or a unit with no provenance (written by hand), is listed as `held`.
`--restale` redrafts a held unit that is stale, turning it back into
`machine`; a fresh reviewed unit and a unit with no provenance are never
touched. An English-root entry whose `lang` is the target locale (the
Venezuela guide in Spanish) is its own translation and is skipped.

What a draft translates:

- **Catalog:** every message string, each plural variant separately; the
  declarations and selectors stay as they are.
- **Page copy (`pages`):** every string except the identifier keys
  (`IDENTIFIER_KEYS` in `src/utils/localize.mjs`), so the translated copy
  passes the shape check in `getPageEntry`.
- **Other collections:** the Markdown body plus the frontmatter keys in
  `FRONTMATTER_KEYS` (`title`, `description`, `summary`, an article's FAQ
  `q` and `a`, a guide's `country`, …) in `scripts/i18n/pipeline.mjs`.
  Dates, statuses, codes, tags and categories are data and stay English. `lang` and `slug` are dropped.
- **Overlays:** the fields in `OVERLAY_FIELDS` (glossary `term` and
  `definition`, opcode and project `description`).

### What a draft keeps

Before a text goes to the model, everything it must not change is swapped
for a token (`⟦3⟧`) and swapped back after (`scripts/i18n/protect.mjs`):
fenced and inline code, HTML tags, link targets, URLs, placeholders such as
`{count}`, opcode names (`OP_CHECKSIG`) and the do-not-translate terms. So
they come back byte-identical whatever the model writes. A reply that drops,
repeats or invents a token, or changes the Markdown heading outline, is
retried once and then reported as `FAILED`; it is never written.

- **Do-not-translate list:** `src/i18n/glossary/dnt.txt`, one term per line,
  case-sensitive, whole words. Every project name in
  `src/data/projects.json` is added automatically.
- **Terminology:** `src/i18n/glossary/<locale>.json` maps an English term to
  the translation the locale uses (`{ "wallet": "billetera" }`). Where a
  choice was made, the value is an object with the reason:
  `{ "wallet": { "translation": "billetera", "note": "Not monedero." } }`.
  It goes with every request; the model is told to use it. It is a request,
  not a guarantee: the reviewer checks it.
- **Style brief:** `src/i18n/glossary/<locale>.style.md`, when it exists,
  goes with every request too: register, vocabulary, number and date format,
  capitalisation. It is a short version of the locale's full style guide
  (`docs/i18n/es-style.md` for Spanish); keep the two in step.

### Review: `pnpm i18n:review <locale> <path> --reviewer "<name>"`

The reviewer reads the draft against the English, fixes it in place, then:

```sh
pnpm i18n:review es src/content/chips/es/chip-2021-01-pmv3.md --reviewer "Ana Pérez"
pnpm i18n:review es messages/es.json --reviewer "Ana Pérez"
pnpm i18n:review es src/data/i18n/es/glossary.json --reviewer "Ana Pérez"
```

It sets `status: reviewed`, records the reviewer (keeping the translator)
and stamps the current English `sourceHash`. A catalog or overlay path
reviews every unit in the file. A unit already reviewed against the current
English is skipped and keeps its earlier reviewer's credit; this applies to
a content file too. Only the `translation` block of a content
file is rewritten; the rest of the file keeps the reviewer's formatting.

**It refuses when the English changed since the draft**, naming what
changed: the reviewer was looking at a translation of older English. Either
compare it with the current English, fix it and re-run with `--rechecked`,
or redraft it with `pnpm i18n:draft <locale> --only <path> --restale` and
review the new draft.

**Bulk: `--only <glob>`** in place of the path reviews every translation
file of the locale that matches the glob. A refused file is reported and
the others still go through; the run exits 1 if any file was refused or
nothing matched. `--rechecked` takes one path, never `--only`: it vouches
that a person compared that file with its new English.

```sh
pnpm i18n:review es --only 'src/content/chips/es/**' --reviewer "Ana Pérez"
```

The CLI, `--only` and the review console all approve through one function,
`review` in `scripts/i18n/pipeline.mjs`. Its `keys` option narrows a catalog
to some message keys, or an overlay to some `<id>.<field>` units.

### Review console: `pnpm i18n:review-ui [locale]`

A local page for working through the drafts one decision at a time
(`scripts/i18n/review-ui.mjs`, logic in `console.mjs`). It binds to
`127.0.0.1` only, on port 4330 (`--port <n>` to change it). It is not part
of the site build and is never deployed: it reads and writes the working
tree, like the CLI.

```sh
pnpm i18n:qa es --fix        # first: the console reads the QA report
pnpm i18n:review-ui es       # then open http://127.0.0.1:4330/
```

The reviewer's name comes from `I18N_REVIEWER`. Without it the console asks
once at startup, offering George Donnelly as the default for `es`. With no
terminal to ask on (run in the background or from a script), it refuses to
start until `I18N_REVIEWER` is set.

It shows one row per fresh `machine` unit, with the English and the draft
side by side, string by string. Rows are grouped by area: the collection,
the overlay file, or for the catalog the key prefix (`catalog: nav`). Each
row carries its QA verdict and reason from `i18n-qa/<locale>.json`. Flagged
rows come first by severity, then unchecked, sent back, fixed and clean.
A row is **unchecked** when QA has no verdict for the text the repo holds
now: QA never saw it, the draft changed since, or QA suggested a fix
without writing it (a run without `--fix`). A flag on any string of a unit
outranks unchecked; the reason lists both.

Every action names the text the console showed (a hash of the English and
the draft). If either changed on disk since the page loaded, the action is
refused and the page must be reloaded, so the console never approves text
the reviewer did not see, and an edit never overwrites a newer draft. An
edit writes only the strings the reviewer changed.

| Key | Action |
|---|---|
| `j` / `k` | next / previous row (opens it, closes the last) |
| `o` | open or close the row |
| `a` | approve |
| `e` | edit, then `Ctrl`+`Enter` to save and approve, `Esc` to cancel |
| `s` | send back with a note (an empty note clears it) |

- **Approve** stamps the unit through `review`: `status: reviewed`, the
  reviewer, the sourceHash check. A unit whose English changed is refused.
- **Edit then approve** writes the edited strings into the draft, then
  approves it.
- **Send back** records a note in `i18n-review/<locale>.json` (committed),
  keyed by unit id, for whoever redrafts or fixes it. The note holds the
  hash of the text it is about, so it lapses as soon as the draft or the
  English changes; approving the unit clears it. A sent-back row is never
  approved in bulk.
- **Approve all clean**, per group, approves only rows QA rated `clean` or
  `fixed` that the reviewer has opened on screen (marked `seen`) and that
  were not sent back. The server checks the rating again before approving.

The server answers only requests addressed to `127.0.0.1` or `localhost`
on its port, and takes writes only as same-origin JSON, so another site
open in the browser cannot drive it.

### Reading copy: `pnpm i18n:reading-copy <locale> [--only <glob>]`

One static page with every translation of a locale beside its English, for
reading it all in one pass on any device (`scripts/i18n/reading-cli.mjs`,
logic in `reading.mjs`). It needs no server: open the file, or copy it to a
phone. It is gitignored and never deployed.

```sh
pnpm i18n:qa es --fix            # first: the copy shows the QA flags
pnpm i18n:reading-copy es        # writes i18n-qa/es-reading/index.html
pnpm i18n:review es --from ~/Downloads/es-reading-notes.json --reviewer "George Donnelly"
```

- **Index:** one row per area: UI strings, each page, each collection
  (blog posts, CHIPs, upgrades…), the glossary, opcodes and the directory.
  Each row has its unit, `machine`, `reviewed` and QA flag counts. The
  `machine` total equals `i18n:check`'s `machine` count, less any stale
  machine drafts, which the index names and leaves out (redraft them first).
- **Areas:** English on the left, the translation on the right, stacked on a
  phone. A Markdown body is rendered and paired paragraph by paragraph; when
  the paragraph counts differ, the body is shown whole with a warning.
  Frontmatter and data fields appear as labelled rows. A flagged unit has a
  coloured edge, its worst severity, and each flagged field's reason. A
  `reviewed` unit is dimmed and has no controls.
- **Marks:** each `machine` unit has a "Looks good" box and a note. Marks
  stay in the browser (`localStorage`) and lapse once the unit's text
  changes in a newer copy. "Export notes" saves `<locale>-reading-notes.json`:
  a list of `{ unit, viewHash, verdict, note }`, where `verdict` is `good` or
  `fix` (a note without "Looks good").
- **`i18n:review --from`** approves every `good` unit through `approve`, the
  console's function. A unit whose draft or English changed since the copy
  was generated is refused. It then prints every note as a to-fix list, the
  notes on approved units included. Fixes go through the console or the
  files, never the reading copy.

The page loads nothing from the network, and a Content-Security-Policy
runs only its own script, so markup in a draft cannot run.

### QA: `pnpm i18n:qa <locale>`

Before a person reads the drafts, a QA pass checks every one of them, fixes
the safe problems and ranks the rest, so the review can start with what
needs judgment.

```sh
pnpm i18n:qa es --dry-run                       # deterministic checks only
pnpm i18n:qa es --only 'src/content/chips/**'   # one area, report only
pnpm i18n:qa es --fix                           # everything, fixes written
```

It reads every fresh `machine` unit: a stale one (English changed since the
draft) is counted and skipped, since it needs a redraft, and a `reviewed`
unit is never read or written. Each string of a unit gets two passes
(`scripts/i18n/qa.mjs`):

1. **Deterministic checks**, no API call:
   - **glossary**: an English term from `src/i18n/glossary/<locale>.json`
     in the source whose rendering is missing from the draft. Renderings
     match as word stems, so an inflected form passes. A label (a
     title-case rendering such as `Support` → `Ayuda`) applies only to a
     string that is the label alone.
   - **register**: *usted* forms against the *tú* rule: `usted`, `su`/`sus`
     for the English *your*, and a formal imperative opening a sentence
     (`Descargue`, `Asegúrese`).
   - **protected**: every code span, URL, HTML tag, link target,
     placeholder, opcode and do-not-translate name of the English comes
     back unchanged.
   - **untranslated**: an English sentence left in the draft, or a draft
     identical to its English. An English document title (`sources[].title`)
     stays English and is not flagged.
   - **format**: decimal point, English thousands comma, a separator in a
     four-digit number, no no-break space before `%`, and English date forms
     (`docs/i18n/es-style.md`).
2. **Model review**: the model `pnpm i18n:draft` uses reads the English, the
   draft, the glossary, the style brief and the check findings, and returns
   `clean`, `fixed` with the corrected text, or `flag` with a reason and a
   severity (meaning drift, omissions, additions, literal phrasing). A fix
   that changes protected text or the heading outline is turned into a flag
   and never written.

`--dry-run` runs only the first pass, calls no API and writes nothing.
Without `--fix` the report is written and nothing else. With `--fix`, each
usable fix is written into the draft, which **stays `machine`**, and every
unit the model reviewed gets a `qaHash` in its provenance: a hash of its
`sourceHash` and the draft text QA left. A later run skips a unit whose
`qaHash` still matches and keeps its rows from the last report; editing the
draft or the English sends it through QA again. Marking a unit `reviewed` is
the reviewer's job, never QA's.

#### The report: `i18n-qa/<locale>.json`

Gitignored and rewritten by every run that calls the model (a run with
`--only` keeps the other units' rows). It is the input of the review
console.

```json
{
  "locale": "es",
  "model": "claude-opus-5-5",
  "generatedAt": "2026-11-19T18:00:00.000Z",
  "rows": [
    {
      "unit": "src/data/i18n/es/glossary.json fee.term",
      "path": "src/data/i18n/es/glossary.json",
      "key": "fee.term",
      "kind": "overlay",
      "area": "glossary",
      "verdict": "fixed",
      "severity": "low",
      "reason": "Used the glossary term comisión.",
      "checks": [],
      "en": "Fee",
      "es": "Comisión",
      "fix": "Comisión",
      "applied": true
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `unit` | the unit's id: the file for content, `<file> <key>` for a message or an overlay field |
| `path` | the translation file |
| `key` | message key, or overlay `<id>.<field>`; absent for content |
| `field` | content: the frontmatter path (`title`, `faq.0.a`) or `body`, one row per field, so a content file has several rows; catalog: the variant path of a plural message (`0.match.count=one`), absent for a plain string |
| `kind`, `area` | `catalog`, `content` or `overlay`; the area is `catalog`, the collection, or the overlay file |
| `verdict` | `clean`, `fixed` or `flag`. A row the checks still fault after QA is a `flag` |
| `severity` | `high`, `medium` or `low` for a flag, `low` for a fix, `null` when clean |
| `reason` | the model's reason, then each check finding, `; `-joined; `null` when clean |
| `checks` | the check findings left after QA: `{ check, severity, message }` |
| `en` | the English |
| `es` | the draft as the repo now holds it (the fix, when applied) |
| `fix`, `applied` | only on a fix: the corrected text and whether `--fix` wrote it |

The run also prints the rows by area and severity.

## Notices and credit

A translated page tells the reader how far to trust it.
`getTranslationState(collection, slug, locale)` in `src/utils/l10n.ts`
returns the entry's `status`, `translator`, `reviewer` and whether it is
stale; `<TranslationNotice state={…}>`
(`src/components/common/TranslationNotice.astro`) renders it from the
catalog:

| State | Shows | Message |
|---|---|---|
| `machine` | a notice | `translation_notice_machine` ("Traducción automática: …") |
| `reviewed`, stale | a notice | `translation_notice_stale` ("may be out of date") |
| `reviewed`, fresh | the credit | `translation_credit` ("Traducción revisada por {reviewer}.") |

Every locale page built from a translated entry must render
`<TranslationNotice>` near its title. The element carries
`data-translation="machine|stale|reviewed"` so a check can count states in
`dist`.

Credit rules:

- The reviewer's name is shown as they gave it to `--reviewer`. Ask how they
  want to be credited; a handle is fine.
- Credit goes to the reviewer, never to the model: a machine draft shows the
  notice, not "translated by Claude".
- A stale page drops the credit for the out-of-date notice until someone
  reviews it again: the credit vouches for the current English only.

`/es/prueba-traduccion/automatica`, `/desactualizada` and `/revisada` are the
fixtures, one per state (`src/content/pages/es/i18n-fixture-*.yaml`).

## Blog posts

A translated post at `src/content/post/<code>/<slug>.md` builds at
`/<code>/<English permalink>` (`es/tokenstork.md` → `/es/blog/tokenstork`) through
`src/pages/[locale]/[...blog].astro` and `getStaticPathsLocalizedBlogPost()`
in `src/utils/blog.ts` (PAN-391). An English post with no translation gets
no locale route. The words (title, excerpt, body, `metadata`) come from the
translation; dates, image, category, tags, author, robots and OG images stay the English
post's. The page is canonical to itself, so it joins the hreflang cluster
with its English original, and it shows `<TranslationNotice>` under the date
line. Both routes render `src/components/blog/PostPage.astro`.

**Out of scope for now:** the locale blog list (`/<code>/blog`), category
and tag archives. They stay English-only, so a translated post's category,
tag and back-to-blog links lead to the English archives.

## Adding a language

1. **Registry.** Add one entry to `LOCALES` in `src/i18n/locales.ts` with
   `status: "draft"`. The inlang settings, routing, content loaders and
   `<html lang dir>` all follow from it. A draft locale builds, but its
   pages are `noindex` and stay out of the sitemap.
2. **Glossary.** Write `src/i18n/glossary/<code>.json` with the locale's
   terminology; add any new do-not-translate term to `dnt.txt`. Write the
   style guide `docs/i18n/<code>-style.md` and its short brief
   `src/i18n/glossary/<code>.style.md`.
3. **Draft.** `pnpm i18n:draft <code> --dry-run` to see the size, then
   `pnpm i18n:draft <code>`, area by area with `--only`.
4. **Review.** A native speaker reviews each file with `pnpm i18n:review`.
5. **Go live.** When the pages that matter are reviewed, flip the entry's
   `status` to `"live"`. Pages still in `machine` keep their notice.

The fallback policy above holds for every new language: no locale route
without a locale entry, and an English fragment inside a locale page is
marked `lang="en" data-l10n-fallback`.

## Search signals

`hreflang`, the sitemap alternates and per-locale feeds (PAN-380).

- **hreflang** is written after the build by `src/i18n/alternates.mjs`,
  since a page cannot know at render time which locales built a counterpart.
  It groups pages by their path without the locale prefix (`/about`,
  `/es/about`). A page joins a group only when its locale is `live`, it is
  indexable, its canonical is itself and its `<html lang>` is its route
  locale's (so a Spanish guide at an unprefixed URL never stands in for
  English). A group of two or more gets the full set on every member: one
  `<link rel="alternate" hreflang>` per member, `x-default` pointing at the
  English page, and `og:locale:alternate` for the other members. A page with
  no live counterpart gets none. Never hand-write hreflang in a page.
- **The sitemap** carries the same groups as `xhtml:link`, through the
  sitemap integration's `serialize`. Draft locales stay out of it.
- **Feeds:** `/rss.xml` is English. `/<code>/rss.xml` exists for each live
  locale with a translated post whose English original is published. Its
  items link to `/<code>/<post>`, which `src/pages/[locale]/[...blog].astro`
  builds (below).
- **JSON-LD** of a creative work (WebSite, Article, BlogPosting, FAQPage,
  Dataset, DefinedTermSet) carries `inLanguage` from the route's locale (or, for
  guides, the entry's own `lang`). `og:locale` comes from the registry.
- **Check:** `pnpm i18n:check:dist` (`scripts/check-i18n-seo.mjs`, see
  Checks below) reads
  `dist` and fails on a missing or one-way hreflang target, a draft page in
  a group or the sitemap, a locale page that is not canonical to itself, a
  sitemap entry whose alternates differ from its page, or a feed item whose
  page was not built.

## Locale routes

A page gets a locale route only where its locale entry exists:

- `src/pages/[locale]/index.astro` builds `/<code>` for each locale with
  `src/content/pages/<code>/index.yaml`. The page body is
  `src/components/home/HomePage.astro`, shared with `/`.
- `src/pages/[locale]/[page].astro` builds `/<code>/<slug>` for the
  top-level pages (PAN-386). Each page body lives in
  `src/components/pages/<Name>Page.astro`, takes its copy and
  `translation` state as props, and is shared with the English
  `src/pages/<slug>.astro`. `LOCALIZED_PAGES` in
  `src/components/pages/index.ts` lists them; `LOCALIZED_REFERENCE` lists the
  `reference` articles (`is-bitcoin-cash-dead`) that build there too.
- `src/pages/[locale]/[...blog].astro` builds `/<code>/blog/<post>` for
  each post translated into that locale (PAN-391). The home page's latest
  posts list only those, through `findLatestPosts({ locale })` in
  `src/utils/blog.ts`.
- `src/pages/[locale]/guides/[slug].astro`, `compare/[slug].astro` and
  `state-of-bch/[month].astro` build `/<code>/guides/<slug>`,
  `/<code>/compare/<slug>` and `/<code>/state-of-bch/<month>` for each
  translated entry. Compare and State of BCH also need their page copy
  (`compare-entry`, `state-of-bch-entry`) in that locale. A guide written in
  the locale (Venezuela, Argentina and Colombia in Spanish) is its own
  original at `/guides/<slug>` and gets no locale route. Each renders
  `<ArticleShell lang={locale} translation={…}>`, so `PageLayout` shows the
  `<TranslationNotice>`. The index pages (`/guides`, `/compare`,
  `/state-of-bch`) stay English for now.

To translate another page: move its body into `src/components/pages/`, add it
to `LOCALIZED_PAGES`, and draft its copy. `PageLayout` shows the
`<TranslationNotice>` above the content when a page passes `translation`.

**Directory lists on a locale page.** `getProjectsByCategory(category,
locale)` in `src/utils/projects.ts` takes each project description from the
`projects` overlay, else English marked as a fallback fragment (`Boxes`
renders it inside `lang="en"`). Where the English list leads with US-only
options, `src/i18n/regional-order.ts` names the projects that lead it in that
locale (on `/es`: Latin American and worldwide buying and spending options
first). It only reorders; a missing regional project belongs in
`src/data/projects.json`.

## Checks

Two commands, both run by `.github/workflows/i18n.yml` on every push and
pull request to `main`. Cloudflare Pages deploys `main` on its own, so a red
run never blocks a deploy, and `pnpm build` runs neither check.

### `pnpm i18n:check` (source; part of `pnpm check`)

`scripts/i18n/check.mjs` reports, per locale:

| Finding | What it means | Live locale | Draft locale |
|---|---|---|---|
| `missing` | a catalog key English has and the locale lacks | fails | warns |
| `placeholder` | a translation's `{placeholders}`, plural inputs or selectors differ from English, or a plural has no `=*` variant (catalog, page copy, overlays) | fails | warns |
| `orphan` | a catalog key, content file or overlay id whose English is gone | fails | warns |
| `machine` | a unit still in machine draft | warns | warns |
| `stale` | a reviewed unit whose English changed since review | warns | warns |
| `fragment` | an overlay field that renders as embedded English | warns | warns |

Across the site it also reports catalog keys no source file names (`unused`,
warns) and **hard-coded strings**: text an `.astro` file under `src/` writes
literally, outside `{…}` expressions, `<script>`, `<style>`, `<pre>`,
`<code>` and elements marked `translate="no"`. Pages under
`src/pages/<code>/` are written in that locale and skipped. While any
locale besides English is live, a hard-coded string fails the check; until
then it warns.

It is a heuristic: text inside JSX within an expression (`{items.map(…)}`)
is not seen. The pseudo-locale build below catches those.

**Allowlist:** `src/i18n/hardcoded-allow.txt`. A bare line is a term
removed wherever it appears (brand names, people, code); the
do-not-translate terms in `dnt.txt` count already. A line
`src/<path>.astro: <text>` accepts one exact string. Mark code and other
text that must never be translated `translate="no"` in the markup instead,
which both checks honour.

An English edit only makes units stale, so it can only warn. A new English
catalog key fails the run while a live locale lacks it.

### `pnpm i18n:check:dist` (after a build)

`scripts/check-i18n-seo.mjs` reads `dist` and fails on a one-way or missing
hreflang target, a locale page not canonical to itself, a draft locale in a
hreflang group or the sitemap, a feed item whose page was not built, a link
from a live page to a draft locale, and a locale page that links to an
English page whose counterpart in its own locale was built (switcher links
excepted). It lists every embedded English fragment without failing.

## Pseudo-locales

`en-XA` (every letter accented, each word about 40% longer) and `ar-XB`
(each word in a right-to-left override, on an `rtl` page) prove the
foundation holds for any language: text that grows, a mirrored layout, and
no English left behind.

```sh
pnpm i18n:pseudo                      # write en-XA and ar-XB from English
I18N_PSEUDO=1 pnpm build              # build with them in the registry
I18N_PSEUDO=1 pnpm i18n:check:dist    # fail on any un-pseudo'd visible text
pnpm i18n:pseudo --clean              # remove them
```

`scripts/i18n/pseudo.mjs` is a translator for the same `scan` and `draft`
as a real language, so code, links, placeholders and do-not-translate terms
are protected exactly as in a real draft. The output goes where a real
translation would (`messages/en-XA.json`, `src/content/<c>/en-XA/`,
`src/data/i18n/en-XA/`) and is gitignored. Both locales are `draft` and
`PSEUDO_LOCALES` in `src/i18n/locales.ts` joins the registry only when
`I18N_PSEUDO` is set. A pseudo build rewrites `project.inlang/settings.json`;
run `pnpm i18n:compile` after one to restore it.

The check reads the visible text of each pseudo page (text nodes, `<title>`,
`alt`, `title`, `aria-label`, `placeholder`) and fails on an ASCII word left
as it was. It skips do-not-translate and allowlisted terms, URLs, opcode
names, code, `<time>` (Intl output, which has no pseudo-locale data), and
elements that carry `lang`, `translate="no"` or `data-l10n-fallback`.

Code reads left to right in every language: `pre`, `code`, `kbd`, `samp`
and `.cmd` are `direction: ltr` in `src/assets/styles/tailwind.css`.
